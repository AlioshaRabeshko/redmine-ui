# Redmine Workspace — браузерний UX-аудит

Дата перевірки: 2026-10-02  
Середовище: локальний Docker demo, http://127.0.0.1:3010  
Статус документа: браузерний аудит завершено з явно позначеними неперевіреними сценаріями та обмеженнями coverage.

## Межі та безпека перевірки

Перед змінами перевірено `/api/health`: `ok=true`, `mode=demo`, `connected=true`, `readOnly=false`. Усі створені/відредаговані дані — локальні demo fixtures. До Redmine, Trello й інших зовнішніх систем не надсилалися мутації; `.env`, токени та auth headers не читалися й не виводилися. Початкові приклади не видалялися.

Перевірка виконувалась у Chrome через реальний UI, з кліками, клавіатурою, drag-and-drop і reload. Screenshot evidence, надані окремою перевіркою root, перелічені біля відповідних знахідок. Звіт не є підтвердженням production поведінки.

- Issue #issue-example: `EXAMPLE-ARTIFACT ROADMAP-DND`; створено зі статусом To Do, додано до NEXT, перевірено перенесення статусу, після чого прибрано з roadmap.
- Issue #issue-example: `EXAMPLE-ARTIFACT stale status audit`; створено окремою root-перевіркою для спроби повторити stale-status сценарій. Її тест зупинився на неоднозначному drag overlay, тож це не вважається незалежним підтвердженням B2.
- Release `EXAMPLE-ARTIFACT REL-1`: опис `Demo-only release readiness/completion fixture.`; використовувався для перевірки наповнення, блокування/готовності та завершення. У фінальному архівному перегляді він містить #issue-example; #issue-example було вибрано в процесі заповнення, але до archived release воно не входило, тому membership #issue-example не вважається підтвердженим.
- Saved filter `EXAMPLE-ARTIFACT`: фільтр статусу Review; перевірено застосування після reload. Він залишився у demo.

## Підтверджені проблеми

### B1 — keyboard shortcuts можуть діяти на іншу картку, ніж сфокусована (P1)

**Відтворення:** відкрити #issue-example → Esc → перевести фокус на картку #issue-example → натиснути Meta+C, Meta+Shift+C або S.  
**Очікується:** скопійовані URL/branch і швидкий статус стосуються сфокусованої #issue-example.  
**Фактично:** копіюються URL і branch #issue-example; S відкриває Quick Move Dialog для #issue-example, де статус показано Suspended, хоча focus має #issue-example.  
**Вплив:** користувач може скопіювати чи змінити не ту задачу.  
**Evidence:** самостійне відтворення виконала окрема root Chrome-перевірка; `/tmp/redmine-ux-root-wrong-shortcut-target.png`. Зовнішніх переходів/мутацій не було.

### B2 — відкрита картка після DnD зберігає застаріле значення статусу (P1)

**Відтворення:** відкрити деталі #issue-example зі статусом To Do → встановити Release=NEXT і натиснути Save Changes → після закриття форми на дошці перетягнути #issue-example із NEXT у Deploy → відкрити деталі картки знову.  
**Очікується:** після переходу статус у формі синхронізований з актуальним або форма позначена як застаріла; збереження не повертає попередній статус непомітно.  
**Фактично:** після DnD заголовок деталей і картка показують Deploy, але поле статусу форми лишається To Do; натискання Save Changes зі старим значенням повернуло задачу до To Do. Для завершення сценарію статус вручну знову встановлено в Deploy і збережено, після чого #issue-example прибрано з NEXT. Аналогічне розходження спостерігалося на #issue-example після переходів Review→QA→ToDo.  
**Вплив:** випадковий запис застарілого поля може непомітно змінити workflow status.  
**Evidence:** самостійне відтворення в локальному Chrome UI; root окремо пробував відтворити на #issue-example, але зупинився на drag overlay і його спробу не вважати підтвердженням. Demo стан #issue-example після мого сценарію навмисно залишено з Deploy і без roadmap membership.

### B3 — помилка створення релізу не видима поверх модального вікна (P2)

**Відтворення:** сторінка релізів → Новий реліз → ввести назву → перехопити POST `/api/commands` mock-відповіддю 503 з `code=CONNECTION` → submit.  
**Очікується:** причина помилки показана всередині активного modal; відхилення обробляється без unhandled rejection.  
**Фактично:** modal залишається відкритою, значення поля збережено, але Error Notice малюється під затіненим backdrop і не читається; водночас зафіксовано unhandled rejection з тим самим текстом. Запит перехоплено до сервера, реліз не створено.  
**Evidence:** окремо підтверджено root; `/tmp/redmine-ux-root-release-error.png`.

### B4 — фокус modal відбирає фокус у поля назви задачі (P2)

**Відтворення:** відкрити створення задачі й почекати щонайменше 100 мс.  
**Очікується:** курсор одразу в полі назви, можна почати друкувати.  
**Фактично:** активним лишається `DIV` контейнер діалогу, а не input; для введення назви необхідно окремо клікнути поле.  
**Evidence:** незалежна root перевірка через Chrome зафіксувала `activeElement=DIV[testId=issue-dialog]`; також підтверджено під час ручного відкриття форми.

### B5 — очищення дати релізу не надсилає очищене значення (P2; request evidence)

**Відтворення:** відкрити `2026.10 Core` → Редагувати → очистити встановлену дату → Зберегти.  
**Очікується:** request містить `dueDate: null` (або еквівалент команди очищення), і дата зберігається порожньою.  
**Фактично:** date input у modal порожній, але updateRelease command не містить поле `dueDate`; тому UI request не виражає очищення. Серверне end-to-end збереження не заявляємо як перевірене.  
**Evidence:** окремо підтверджено root через перехоплення browser request; payload мав `name` і `description`, `dueDateSent=false`; перевірено узгодженість із командним обробником.

### B6 — поле пошуку обіцяє labels і людей, яких пошук не знаходить (P2)

**Відтворення:** Core API → Усі задачі → ввести `incident` у пошук.  
**Очікується:** знаходиться #issue-example, бо вона має label `incident`; placeholder також прямо обіцяє пошук labels і людей.  
**Фактично:** показано 0 карток і порожній стан “За цими фільтрами задач не знайдено”.  
**Evidence:** окрема root Chrome-перевірка; screenshot `/tmp/redmine-ux-root-search-label.png`. Текст placeholder: `Пошук задач, міток, людей…`.

### B7 — у виборі задач для релізу замість статусу показано “Фактичний статус” (P2)

**Відтворення:** створення/редагування релізу → поле додавання задач → відфільтрувати `EXAMPLE-ARTIFACT`.  
**Очікується:** кожний рядок показує зрозумілий фактичний статус задачі, необхідний для перевірки готовності.  
**Фактично:** у рядках власних задач відображається буквальний текст `Фактичний статус`, тоді як у деталях релізу для тих самих задач після додавання видно To Do або Deploy.  
**Вплив:** до додавання задачі користувачу важко визначити, чи вона блокує завершення.  
**Evidence:** UI та accessibility tree форми релізу в Chrome.

## UX-покращення та менш критичні спостереження

- Стислий закритий control сортування показує лише `За спаданням`, без активного поля сортування. Після відкриття меню обраний параметр видимий у відповідній optgroup. Це ускладнює розуміння застосованого сортування, але саме сортування Number/ID descending фактично змінює порядок карток (#issue-example перед #issue-example у To Do). **Evidence:** реальний board UI.
- Status і priority подані нативними multiple listbox. Послідовні звичайні кліки In Progress→Review і High→Urgent залишили лише останній вибір; priority давав 2 задачі після вибору Urgent. Доступний спосіб утримати кілька варіантів через modifier не було підказано біля контролу й окремо не перевірено. Це підтверджує UX-фрикцію, яку користувач попросив усунути кастомними checkbox/chips; саме поведінка з modifier лишається неперевіреною.
- На мобільній ширині 390×844 кнопка toggle sidebar прихована; навігаційні `.nav-item` мають `aria-label`. Це окремо перевірив root. Потрібно оцінити, чи мобільний layout залишає очевидний спосіб дістатися до всіх розділів; поки це UX-питання, не підтверджена недоступність навігації.
- Для короткої keyboard-навігації у select статусу створення спостерігався submit форми замість очікуваної зміни опції, але кейс ще не повторений незалежно; він не включений як підтверджений дефект.
- У формі коментаря дві спроби Super/Cmd+Enter лишили текст у полі; явний клік “Додати коментар” спрацював. Це не позначено дефектом: Cmd/Ctrl+Enter у RESEARCH §10.1 є пропозицією, а не погодженою поведінкою.
- Налаштування мають явну кнопку “Зберегти налаштування”. Зміна locale без save не перекладає UI; після переходу на дошку й повернення мова без попередження повернулась до збереженої. Це може бути очікуваною моделлю незбережених форм, але відсутність індикатора/попередження створює ризик втрати змін.
- Додатково перевірено збереження чернеток: текст опису та коментаря #issue-example відновилися після закриття/повторного відкриття й після reload; незбережені поля створення задачі відновилися після закриття та reload. Тестові чернетки після перевірки очищено, жодної задачі з них не створено.
- Налаштування keyboard shortcut діють після збереження: тимчасова зміна створення задачі з N на Alt+N відкривала форму лише за Alt+N; N більше не відкривав її. Значення відновлено до N. У текстовому полі пошуку N додавався як текст і не запускав shortcut; Meta+C копіював виділений рядок поля (`copy-guard`), не URL картки. Поза полем N відкрив порожню форму створення, яку скасовано.
- QA override перевірений на власній #issue-example: тимчасово змінено project default QA Example Project з Example Person A на Example Person B; у деталях status Review збережено, потім перехід Review→QA вибором статусу призначив Example Person B як QA. Після тесту status повернуто в Deploy, QA role — Example Person A; project default теж повернуто до Example Person A. Окремо раніше DnD перевіряв Review→QA із default QA та QA→ToDo із поверненням assignee до Example Person B.
- У Settings Automation було увімкнене background automation з інтервалом 30 секунд. Інтервал тимчасово збережено як 45 і відновлено 30; automation залишилась увімкненою. Кнопка “Синхронізувати” в demo показала “Оновлено 10:41”. Автоматизацію, що змінює задачі, окремо не запускав.
- Поточна сторінка має `<link rel=icon href="/favicon.svg">`; після читання останнього unread у inbox він був 0. Динамічну зміну favicon при наявності unread badge не підтверджено.
- Root Chrome перевірив 390×844: collapse control sidebar приховано на цій ширині, nav links мають `aria-label`. Це спостереження про мобільне представлення; доступність переходів у кожен розділ не доводить недоступною.

## Пройдені сценарії та результати

- **Стартовий стан і режим:** health endpoint підтвердив demo; початковий board Example Project завантажився, показав seed issues і окремі NEXT/release lanes.
- **Sidebar і проєкти:** collapse/expand sidebar повторно перевірено після reload на desktop і працює; перемикання Core API ↔ Example Project працює. Root підтвердив mobile ширину 390×844: toggle sidebar приховано, nav links мають доступні назви.
- **Подання:** All Tasks, Assigned Me, Watching і Backlog відкриваються. Assigned Me був порожній та показав пояснення/CTA; Backlog показав #issue-example. Watching у seed data не дозволив зробити висновок, що непереглянуті задачі фільтруються коректно, бо тестові задачі створювались поточним користувачем.
- **Фільтри та пошук:** status/priority listbox застосовуються відразу; наступний звичайний click замінює попередній вибір, а багатовибір через modifier не перевірено. Clear повернув усі lane. Пошук і статусний фільтр взаємодіють як обмеження разом; неможливий query прибрав картки й показав empty state. Search-label mismatch описаний як B6.
- **Збережений фільтр:** `EXAMPLE-ARTIFACT` створено, повторно застосовано після очищення та після reload. Фільтр залишений у demo.
- **Сортування:** Number/ID descending переставив задачі у lane очікувано; закритий control приховав ключ поля сортування.
- **Roadmap, статус та DnD:** #issue-example додано до NEXT при фактичному To Do. Card показала NEXT, To Do і попередження; перетягування в Deploy змінило реальний статус, лишивши membership у NEXT, після чого попередження зникло. У деталях вибір “Прибрати з роадмапи” зняв membership і показав картку у Deploy. Це відповідає вимозі пріоритету roadmap membership із показом actual status. Саме на #issue-example також відтворено B2.
- **Перехід Review→QA→ToDo:** #issue-example вручну створено зі статусом Review; drag у QA перевів фактичний статус у QA і призначив QA Example Person A; drag назад у ToDo повернув assignee Example Person B, зберігши QA role Example Person A. Окремий прямий Review→ToDo через поле статусу в деталях так само повернув assignee Example Person B. Додатково в Settings тимчасовий QA override Example Person B спрацював для переходу Review→QA у деталях; згодом card status/QA role та project default відновлено до Deploy/Example Person A.
- **Картка, branch, коментарі:** створена #issue-example отримала branch `2009-EXAMPLE-ARTIFACT`; кнопка копіювання показала toast “Скопійовано”. Два точні тестові коментарі додані вручну. Cmd/Ctrl+Enter залишився лише UX-пропозицією; keyboard copy shortcut окремо не повторювався тут, бо wrong-active-card випадок B1 підтверджено root.
- **Релізи:** у вихідному переліку були активні Example Release і NEXT, закритий Example Release. Створено `EXAMPLE-ARTIFACT REL-1`; readiness був заблокований, поки незавершена задача була поза Deploy, і став готовим після переходу задачі до Deploy. Натискання “Завершити реліз” перемістило REL-1 до архіву. Архівний перегляд показав #issue-example у Done та лічильник однієї завершеної задачі; #issue-example лишився Deploy на дошці та в archived release не присутній, тому його членство в REL-1 не підтверджено. Done і Rejected за замовчуванням приховано; увімкнення “Показувати Done і Rejected” показало Done lane із #issue-example. У виборі задач для наповнення релізу для власних задач показується буквальний `Фактичний статус` (B7). Окремо B3 error та B5 clear-date — request/mock evidence.
- **Inbox та архів:** вхідні сповіщення показували 1 unread. Відкриття notification про коментар Example Person A на #issue-example перемкнуло проект на Core API, відкрило issue details і зменшило unread до 0. Архів показав 2 записи; кнопка “Непрочитані” повернула порожнє unread-подання. Не створював штучних сповіщень для перевірки власного коментаря.
- **Локаль, тема та акцент:** усі 4 locales (uk/pl/es/en) вручну застосовані через Settings і переклали основні елементи UI. Light дав background `rgb(246, 247, 250)`; dark — `rgb(21, 25, 35)`; system обрав dark згідно з системною темою. Усі 4 палітри blue/violet/green/amber збережені, підтверджено через `data-palette`; фінальне повернення до uk/system/blue збережено. Reload підтвердив persistence: `lang=uk`, `data-theme-choice=system`, `data-theme=dark`, `data-palette=blue`.
- **Shortcuts і текстові поля:** значення default mappings переглянуто в Settings. Перевірено N у полі пошуку (вставляє символ, не створює задачу), Meta+C по виділеному пошуковому тексту (звичайне копіювання), N поза текстовим полем (відкриває форму). Для configuration відтворено й відновлено Alt+N override. Незалежний root сценарій wrong-card URL/branch/S залишається B1.
- **Чернетки:** unsent comment draft на #issue-example повернувся після close/reopen і reload; description draft показав “Чернетку збережено локально” і повернувся після reload; create-form title/description повернулися після close/reopen та reload. Усі draft test strings очищено, не submitted.
- **Automation/settings:** інтервал 30→45 зберігся, після тесту повернуто 30; checkbox background automation весь час лишався ввімкненим. Демо Sync Now завершився статусом “Оновлено 10:41”. Не запускав автоматизацію, яка могла б змінювати задачі.
- **Зовнішні помилки:** B3 перевірено на контрольованому mocked request, що відхилявся до сервера; B5 — через захоплений request payload. Це не були production чи інтеграційні запити.

## Неперевірені сценарії та межі coverage

- Не перевіряв зміну favicon при появі/зникненні unread badge; побачено лише статичний `/favicon.svg` і unread=0 наприкінці.
- Не запускав фонову автоматизацію, що могла б змінювати задачі; перевірено лише settings та безпечну demo-синхронізацію.
- Палітри пройшли застосування й перевірку `data-palette`; pixel-level порівняння screenshot не робив.
- QA override перевірений через status field у деталях, тоді як board DnD окремо перевірений із default QA. Override саме шляхом DnD не проходив.
- Multi-select кількох статусів/пріоритетів, фільтр за пріоритетом і одночасний стан без lane для комбінації фільтрів детально не оцінено. Один статусний фільтр, пошук, clear і empty query перевірені.
- Mobile перевірка обмежена повідомленим root заміром 390×844 (collapse control hidden, nav links мають aria-label); повний mobile layout, keyboard/focus і кілька zoom/breakpoint значень не перевірялися.
- Sort value коректно перебудував lane order, але persistence конкретного sort choice після reload не перевіряв.
- Для notification-архіву перевірено читання й перемикання на unread, але не точну появу notification від власного comment.
- Зміни Settings без Save губляться після navigation; це спостережено в поточній реалізації. Остаточне уточнення користувача вимагає автозбереження налаштувань, крім shortcuts.

## Погоджене обмеження продукту, не баг

Поточна реалізація є локальним demo/read-only для реального Redmine за правилами проєкту. Будь-які недоступні реальні write-команди є погодженим тимчасовим обмеженням у розробці; це не оцінюється як дефект UX demo. Перевірки створення, редагування, переходів, коментарів і релізів у цьому звіті стосуються тільки ізольованого demo.

## Зауваження користувача для наступної UX-переробки

Після першого переліку знахідок користувач попросив спершу зафіксувати проблеми й власні UX-вимоги, а реалізацію відкласти. Погоджений напрям записано в [RESEARCH.md §19](RESEARCH.md) та [TECHNICAL.md §14](TECHNICAL.md); ці пункти є цільовою поведінкою майбутньої переробки й не означають, що вона вже реалізована або перевірена.

- Замінити панель фільтрів, що штовхає board вниз, на popover/portal поверх дошки; показати активні умови, окреме очищення й швидке очищення; користувальницькі збережені фільтри та кнопки Усі / Мої / Спостерігаю / Беклог розмістити безпосередньо на основній дошці.
- Замість терміна «подання» використовувати «збережений фільтр»; замість native selects у фільтрах — пошук, checkbox і chips, без Ctrl/Cmd для multi-select.
- Додати shared people picker із частими локальними виборами на початку списку, аватаром/ініціалами та відмінною рамкою й текстовим позначенням ролей QA, support і developer. Ролі надходять із Redmine з локальним перевизначенням.
- На існуючій картці статус, assignee, priority, release/roadmap, labels і локальні ролі мають зберігатися одразу після вибору; description і comments лишаються явною дією з локальними draft, що переживають reload. Реальні Redmine write restrictions лишаються чинними.
- У settings розглянути theme buttons і palette swatches; для language/actions/status/labels/sort — спільні custom pickers де це доречно. Закритий sort field має показувати активний критерій та напрямок. Після остаточного уточнення налаштування зберігаються одразу; shortcuts мають окреме явне збереження.

### Додаткові зауваження та вибірковий замір — primary agent

Після завершення аудиту користувач додав: переробити кольори палітр обох тем, підвищити читабельність дрібного тексту зі збереженням компактності; повторне Q вимикає «Мої». Остаточно: S лишається зміною статусу, Cmd/Ctrl+S зберігає поточну форму. Налаштування застосовуються одразу, крім shortcuts з явним збереженням. Мобільний UX відкладено. Вимоги записані в RESEARCH.md §19.5–19.7; раніші припущення про S та відсутність Settings autosave більше не актуальні. Виправлення ще не внесені.

Додатково виміряно computed styles Chrome на локальній дошці для восьми комбінацій light / dark × blue / violet / green / amber. Тема й палітра змінювались лише в DOM тестової вкладки, без збереження налаштувань. Розміри: статус 8 px, label / branch / номер задачі / priority 9 px, підказка дошки 10 px, кнопки / пошук / підзаголовок 11 px. Текст initials малого аватара — 7 px. Це підтверджує дрібну типографіку; розмір сам по собі не є висновком про порушення WCAG.

| Комбінація | Елемент і пара кольорів | Контраст |
| --- | --- | --- |
| Light / green | Активна навігація й label: #issue-example на #e6f5ef | 4.24:1 |
| Light / amber | Активна навігація й label: #a76c15 на #fff3dc | 3.98:1 |
| Light / amber | Активна primary button: #ffffff на #a76c15 | 4.38:1 |

Ці пари нижчі за мінімум 4.5:1 для звичайного тексту [WCAG 2.2](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Це підтверджена проблема контрасту вибраних елементів. Dark та інші пари у цій вибірці не опустились нижче 4.5:1; це не підтверджує контраст усього UI. Placeholder pseudo-elements, hover / focus, графічні елементи, opacity / disabled, gradients та всі форми не охоплені цим заміром. Неприємність відтінків є окремим прямим зауваженням користувача, навіть коли числовий контраст достатній.

### Доповнення: створення з колонки
