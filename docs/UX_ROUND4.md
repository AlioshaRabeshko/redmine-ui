# UX аудит: переміщення, непрочитані події та беклог

Дата: 2026-10-05. Користувач подав п’ять зауважень після увімкнення write mode і попросив обговорити питання/пропозиції. Користувач погодив реалізацію Luna max після обговорення; нижче збережено вимоги та прийняті defaults. Реальних мутацій для дослідження не виконували.

## Вимоги користувача

1. Після drag and drop картка одразу залишається у цільовій колонці з Saving. За невдалого збереження повертається назад. Поточний код показує pending, але не застосовує оптимістичне переміщення: до відповіді сервера використовується стара задача.
2. Дзвіночок непрочитаних має червону заливку та стоїть унизу праворуч, після аватарів. Зберегти кількість непрочитаних і дію відкриття картки/скролу до події.
3. Звичайне відкриття картки теж дозволяє прочитання сповіщення, коли відповідна подія фактично потрапляє у видиму область. Зараз acknowledgement прив’язаний до явного переходу зі сповіщення. Прочитання конкретних подій синхронно прибирає їх із непрочитаного Inbox і зменшує badge/favіcon/counts; у архіві події залишаються.
4. У беклозі є небажаний горизонтальний скрол. Довгі рядки без пробілів — припущення користувача щодо причини, ще не підтверджене браузерним відтворенням. Перевірити intrinsic width, min-width, перенесення назв/міток/інших довгих значень.
5. Беклог стає окремим списковим UI, а не канбаном із колонками. У рядку показувати дату створення та останню активність. Семантика вибірки лишається погодженою раніше: фактичний статус Backlog, із проєктними фільтрами.

## Пропозиції для обговорення

- Автоматичне прочитання: видимий заголовок і початок відповідної події протягом приблизно секунди у активній вкладці. Саме відкриття картки не прочитує всю історію; події поза viewport, приховані Activity-фільтром або буфером нових подій не прочитуються. Довга подія не потребує одночасного вміщення всього тексту на екрані.
- Оптимістичне переміщення зберігається попри старий SSE/poll response до завершення команди. Повторне переміщення тієї самої картки під час Saving заблоковане. Правила Version/status зберігаються: Deploy з активним релізом відображається в колонці релізу; додавання до релізу без Deploy не змінює статус.
- При однозначній відмові без змін — візуальне повернення до попереднього стану й помилка. При частковому workflow (наприклад статус QA вже змінено, а призначення QA відхилене) або невідомому результаті — перечитати й показати фактичний стан Redmine; не зображати успішне повернення, якого на сервері не було, і не робити автоматичних компенсаційних мутацій.
- Список беклога: пріоритет, тип/ID, назва, мітки, люди, створено, остання активність, unread badge. Компактні рядки, назва з переносом довгих слів, клік відкриває чинну картку. Зберегти фільтри, Priority desc за замовчуванням, інше сортування, URL/історію й клавіатуру.
- Остання активність за замовчуванням — Redmine updated_on (коментар або зміна задачі), а не лише дата останнього коментаря. Дати відносні, точна дата/час у tooltip.
- Погоджена швидка дія рядка: «У To Do» для початку роботи без відкриття картки.

Користувач погодив quick action «У To Do» та fallback на фактичний стан Redmine після часткової/невідомої помилки, і дозволив реалізацію Luna max. Інші описані defaults прийнято для реалізації. Mixed notification з одним ID читається автоматично тільки якщо всі представлені у сповіщенні види події показані; проєкція comments-only потребує лише коментаря. Реалізацію і сценарії мутацій перевіряти тільки demo/mocks; write mode приватного Redmine не використовувати для тестових змін.
