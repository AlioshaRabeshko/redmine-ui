# UX round 5: перевірка проблем картки

Перевірка обмежена читанням наявного коду та трьох наданих знімків екрана. Застосунок не запускався, UI не керувався, тести й зовнішні запити не виконувалися. Знімки підтверджують видимі стани; причини нижче, якщо не зазначено інше, встановлені за кодом, а не відтворенням у браузері.

## Дії з коментарями лишаються неактивними

На знімку панелі коментаря видно активні Quote і Link та вимкнені Edit і Delete; Like підписаний як недоступний. Це підтверджено пікселями знімка. Він не показує, який режим застосунку чи набір серверних capabilities його сформував.

Клієнт рендерить Edit/Delete/Like для коментаря, але блокує їх, якщо `journal.canEdit`, `journal.canDelete` або `journal.canLike` не підтверджено: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:910) і [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:936). У real mode сервер дозволяє Edit/Delete лише для власного коментаря та за відповідного capability flag; Like повертається тільки в demo mode: [app.ts](/Users/oleksii/work/redmine-ui/src/server/app.ts:384). Поточний sync записує capability snapshot без `journalEditing` і `journalDeleting`: [service.ts](/Users/oleksii/work/redmine-ui/src/server/sync/service.ts:113). Якщо edit/delete все ж дійдуть до real executor без підтвердженого flag, він поверне capability error до відправлення запиту в Redmine: [real-executor.ts](/Users/oleksii/work/redmine-ui/src/server/commands/real-executor.ts:488).

Висновок: вимкнений стан відповідає консервативному серверному контракту, але код зараз не виявляє й не записує capabilities для real journal edit/delete. Це не доводить, що будь-який Redmine інстанс не підтримує такі дії. Документація round 5 фіксує, що версію цільового інстансу й право поточного користувача перевірити не вдалося; для likes не знайдено офіційного core write endpoint: [UX_ROUND5_BACKEND.md](/Users/oleksii/work/redmine-ui/docs/UX_ROUND5_BACKEND.md:21), [UX_ROUND5_BACKEND.md](/Users/oleksii/work/redmine-ui/docs/UX_ROUND5_BACKEND.md:27). Тож не слід вмикати кнопки за припущенням чи локально імітувати успіх. Якщо потрібні Edit/Delete у real mode, спершу потрібен підтверджений контракт capabilities для конкретного інстансу; likes залишаються окремою plugin/API перевіркою. Для користувача доречно показувати коротку причину недоступності Edit/Delete так само виразно, як недоступність Like.

## Звичайну локальну чернетку не можна відкинути

Кнопки `Discard draft` для назви/опису та гілки з'являються тільки за умов `hasCardTextConflict` і `hasBranchTextConflict`: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:276), [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:879). У звичайному dirty стані форма показує Save changes, але не має кнопки для скасування локального редагування: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:882). Цей висновок підтверджений умовами JSX; інтерактивно форму не відтворювали.

Дія `discardTextDrafts` повертає вибрані поля до поточного `serverTextRef`, позначає їх чистими та очищає їхні scoped draft keys; вона не викликає `onSave` і не надсилає запис у Redmine: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:435). Ключ містить scope застосунку/інстансу/користувача, project ID, issue ID і поле: [App.tsx](/Users/oleksii/work/redmine-ui/src/client/app/App.tsx:1120), [serialFieldWrite.ts](/Users/oleksii/work/redmine-ui/src/client/lib/serialFieldWrite.ts:19). Чернетки зберігаються окремо для полів, а за недоступного `localStorage` застосунок тримає значення або clear marker у пам'яті поточної вкладки: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:363), [draftStorage.ts](/Users/oleksii/work/redmine-ui/src/client/lib/draftStorage.ts:28).

Для інших полів і форм поведінка відрізняється: коментар-композер має `Discard draft`, коли текст не порожній, а редактор існуючого journal має Cancel: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:896), [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:930). Зауваження користувача про «відкинути збережені зміни» неоднозначне. Поточний механізм скасовує лише незбережений локальний draft. Після успішного save форма очищає draft для полів, які не отримали новий текст під час запиту, а UI не має undo для вже застосованої серверної зміни: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:604), [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:620). У UX-тексті варто називати цю дію «Відкинути чернетку», а не «Скасувати зміни»; додати її до звичайного dirty стану назви/опису/гілки, окремо від conflict-повідомлення.

## Відновлена чернетка опису відкриває редактор

Знімки пікселями підтверджують, що UI показував і Preview, і візуальний editor. Вони не доводять, чи була в конкретному відкритті відновлена локальна чернетка.

Під час ініціалізації застосунок читає scoped чернетки, порівнює кожне поле з початковим server value та визначає `initialDirty.description`: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:140), [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:163). Початковий стан preview задається як `!initialDirty.description`: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:210). Отже, якщо відновлений опис відрізняється від server value, картка відразу відкривається в editor. Для чистого опису початковий стан — Preview. Причину конкретного скриншота без стану browser storage встановити не можна.

Це конфлікт із вимогою round 5 показувати Preview за замовчуванням. Пропонований UX: починати в Preview навіть із відновленою чернеткою, показувати явний індикатор «є незбережена чернетка» і за кліком Edit відкривати збережений draft. Preview уже відображає `textDraft.description`, а не лише значення з сервера: [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:875). Так draft лишається видимим і збереженим, але сам факт його наявності не перемикає картку в editor.

## Відкриття картки чекає на оновлення дошки

Причина додаткового очікування встановлена за кодом, але час її впливу на конкретному пристрої не вимірювався. Після отримання issue detail ефект завжди викликає та очікує `fetchQuery` для дошки проєкту, і тільки потім встановлює `freshIssueDetailId`: [App.tsx](/Users/oleksii/work/redmine-ui/src/client/app/App.tsx:497). Діалог показується лише коли detail уже є і цей ID встановлено; до цього залишається spinner: [App.tsx](/Users/oleksii/work/redmine-ui/src/client/app/App.tsx:1118). Кеш дошки може зробити очікування коротким, однак за протермінованого кешу воно додає мережевий запит до шляху відкриття.

IssueDialog завантажується як lazy module, але всередині нього `RichEditor` і `RichContent` імпортуються статично: [App.tsx](/Users/oleksii/work/redmine-ui/src/client/app/App.tsx:23), [IssueDialog.tsx](/Users/oleksii/work/redmine-ui/src/client/features/issues/IssueDialog.tsx:10). Editor напряму імпортує Tiptap, а preview renderer — Markdown parser, sanitization і code highlighter: [RichEditor.tsx](/Users/oleksii/work/redmine-ui/src/client/components/RichEditor.tsx:1), [RichContent.tsx](/Users/oleksii/work/redmine-ui/src/client/components/RichContent.tsx:1). Це підтверджує спільний модульний шлях, але без bundle/performance вимірів не встановлює, що саме він є помітною частиною затримки.

Кандидат на виправлення: показувати діалог після отримання свіжого issue detail, одразу використовувати наявний кеш дошки, а її оновлення виконувати паралельно; поля, яким потрібен ще не завантажений каталог, залишати в loading/disabled стані до завершення запиту. Окремо виміряти час і розмір issue chunk, перш ніж дробити editor/preview на додаткові lazy chunks. Це рекомендації з source audit, не підтверджені runtime-профілюванням.

## Межі доказів

Піксельно перевірено лише вигляд трьох переданих знімків: вимкнені journal actions, відображення Preview та візуального редактора. Умови capabilities, draft restore/discard і порядок fetch встановлено за кодом. Для них не перевірявся конкретний браузерний storage, активний mode, мережевий час, серверна версія або API permission.
