## Початковий контекст обговорення

Користувач додав 18 зауважень після другого раунду й попросив їх обговорити. На цьому етапі змінюється лише документація: код, Docker та чинні налаштування не змінюємо. Заборона зовнішніх мутацій Redmine/Trello залишається чинною. Орієнтир для board unread badge — приклад Trello зі дзвіночком і числом непрочитаних подій.

## Перевірені причини в поточному коді

- `Notification` містить готові `text`, `kind`, IDs, actor, timestamps, без subject і структурованих changes. `SyncService.processJournal` формує text через `${field}: ${oldValue} → ${newValue}`; Inbox показує його напряму. Наявний `localizeJournalChange` використовується лише в issue Activity. Це пояснює сирі field IDs і числові Labels у Inbox; потрібне виправлення як нових, так і вже збережених подій.
- `shouldNotify` використовує `subscribed || assignedToMe`. Відповідно comments-only підписка не обмежує assigned-to-me події. Для змішаного journal категорії визначаються окремо, але `kind` зберігається лише перший. Точну причину конкретної показаної події без перевірки її assignment/source не заявляємо.
- Backend `BackgroundWorker` використовує налаштований interval після завершення sync, default settings — 30 s, при помилках backoff. `App.tsx` уже має `EventSource('/api/events')` та invalidation при `sync`/інших подіях. Unread має 30 s polling, board query власного interval не має. Отже auto-update не є повністю відсутньою можливістю: потрібно перевірити фактичну роботу stream та забезпечити fallback для дошки.
- Поточні avatar board sizes — 34/22 px; toolbar, footer, composer після списку, окремі Activity row/filter row та due date в лівій формі підтверджено читанням компонентів.
- CSS має app-frame `height:100dvh; overflow:hidden` і окремий `.content-scroll`. Це не є доказом відтворення Settings overflow; потрібна браузерна перевірка уточненого користувачем скролу всього застосунку.

## Черга для майбутньої реалізації

1. Notification data/display та точна семантика subscription; subject, людські зміни, старі дані без втрати unread, розгорнуті групи.
2. Спільний unread index, board badges/filter та надійний sync→UI refresh без втрати drafts.
3. Компактний sticky issue layout, composer зверху, Labels tiles/due date, typography/avatar colors; Settings overflow.

Сценарії mutations перевіряти тільки в isolated demo/mocks, real GET/HEAD-only. Усі перелічені пропозиції, де немає прямої вказівки користувача, відрізняються від уже погоджених вимог. Реалізацію цього раунду ще не починали.

## Відповіді користувача

- Comments-only застосовується й до задач, де користувач виконавець. Це уточнює старе «мої задачі завжди»: вони завжди включені в eligibility, але події фільтруються згідно з налаштуванням.
- Settings: за межі viewport прокручується весь застосунок із sidebar і header; потрібно виправляти зовнішній overflow, зберігши внутрішній scroll довгого вмісту.

## Додаткові пропозиції для обговорення

Користувач запитав про решту питань і пропозицій. Нижче — запропонована поведінка, ще не погоджені зміни:

- Клік board badge: рекомендована альтернатива попередній пропозиції переходу в Inbox — відкрити картку на конкретній непрочитаній події, прочитати лише цю подію. Потрібно обрати картку чи Inbox; конкретний target (новіша/старіша непрочитана) також не встановлений. Звичайне відкриття картки не читає автоматично всі її події.
- При автооновленні зберігати dirty drafts, focus, scroll колонок і відкритої картки. Поки користувач читає Activity, нові події не повинні зсувати поточний текст: показувати компактне «Нові події — показати» й оновлювати список за натисканням. Board unread counters оновлюються одразу.
- Якщо активний фільтр «З непрочитаними» й останню подію прочитано, картка може зникнути з дошки, але відкритий dialog залишається до явного закриття. Повернення фокуса має fallback, коли opener вже зник.
- Comments-only для змішаного journal: показувати текст коментаря, без супутніх Labels/status changes, які не відповідають event preference. Категорія визначає як eligibility, так і visible parts, зі збереженням exact journal target.
- Невідомі значення мають зрозумілий fallback; діагностичні сирі ID доступні у technical details, а не основному тексті сповіщення. Старі непрочитані не архівувати автоматично при зміні preferences; за потреби окремо погодити їх visibility за чинним event filter.

Основні продуктові блокери про subscription і Settings вже закриті. Не додавати нові великі функції до поточного раунду; ці пропозиції уточнюють наявні сценарії.

## Погоджені уточнення після обговорення

Користувач підтвердив такі рішення (вони мають пріоритет над попередніми варіантами/пропозиціями цього документа):

1. Board badge відкриває **картку й скролить до непрочитаної події**, замість переходу в Inbox. Звичайне відкриття картки не читає всі її події; зберігаємо event-specific read, без масового архівування решти групи.
2. Якщо картка зникає з дошки через фільтр «З непрочитаними» після прочитання останньої події, відкритий dialog лишається до явного закриття. У разі зникнення opener потрібне коректне повернення фокуса до дошки.
3. Comments-only фільтрує також **вміст** змішаного journal: коментар показуємо, супутні Labels/status changes приховуємо. Це діє також для задач, де користувач виконавець.
4. Під час читання нові події не зсувають поточний вміст: показуємо «Нові події — показати» й застосовуємо оновлення списку за натисканням, зберігаючи drafts/focus/scroll. Дзвіночки та unread counters оновлюються одразу.

Індикатор свіжості даних залишається пропозицією, окремого підтвердження не було. Реалізацію цього раунду ще не починали.

## Початок реалізації — 2026-10-05

Користувач доручив виконати цей раунд через Luna max сабагентів; попередні записи про обговорення/паузу описують історичний стан. Практичні defaults із пропозицій: 10 s sync, розгорнуті Inbox groups, board avatars 30/20 px, компактне меню copy/open та стабільні кольори initials. Badge відкриває найстарішу непрочитану подію задачі, щоб не пропускати накопичені події, й читає лише успішно відкритий target. Реальні записи залишаються заборонені, demo/mocks для mutations. Основний агент координує файли й інтеграцію; незалежний Luna перевірить desktop UX та фактичні сценарії після реалізації.
