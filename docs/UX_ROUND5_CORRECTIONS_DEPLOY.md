# Виправлення UX round 5: розгортання Docker

## Початковий стан

До розгортання контейнер `redmine-ui-app-1` (`7784a8b7bbe9`) працював і мав стан Docker `healthy`; порт був опублікований лише як `127.0.0.1:3010 -> 3000/tcp`. Він використовував образ `redmine-ui-app:latest` (префікс локального ID `948c2939aabb`) та іменований том `redmine-ui_workspace-data:/data`.

Перевірка Dockerfile і Compose підтвердила багатоступеневий образ Node 24, шлях до бази `/data/workspace.sqlite`, типовий порт хоста `3010`, іменований том та HTTP-перевірку `/api/health`. `.dockerignore` виключає `.env`, `.env.*`, файли SQLite й результати збірки та тестів. У Compose є запасне значення-заглушка для `REDMINE_URL`; фактичне значення з `.env` не читали й не змінювали.

## Збірка образу та перевірка SQLite

Першу збірку виконали до завершення перевірки браузера. Typecheck, Vite та серверна TypeScript-компіляція пройшли. Зібраний образ мав дайджест маніфесту `7d61434543d6961055d79824548b8a77373a25d147860a71e79580c69ba60dfb`. Після неї перевірка якості знайшла відтворювану нестабільність вибору зображення в редакторі, тому цей образ не використовували для розгортання.

Після виправлення вибору й фокусу зображення образ зібрали повторно. Typecheck, Vite та серверна TypeScript-компіляція знову пройшли; клієнтська збірка створила файли `RichEditor-W5j181yM.js`, `IssueDialog-n7xOs816.js` і `index-BvAAyVnd.js`. Дайджест маніфесту `redmine-ui-app:latest`: `76903ae078d361c5992dc4f3a0b6b542c53d295208e60ccb152daa21f9a406b2`.

Для цього образу окремо перевірили нативний модуль SQLite у тимчасовому контейнері з `--network none`, без підключених томів і лише з базою `:memory:`. Запит `SELECT 1` успішний: `{"binding":"loaded","query":1,"closed":true}`. Збірка вивела попередження Vite про фрагмент коду понад 500 kB і npm про сценарій встановлення `better-sqlite3`; модуль завантажився, npm повідомив про відсутність вразливостей.

## Розгортання після фінальної перевірки

Після проходження фінального браузерного gate (20/20 зачеплених сценаріїв і 3/3 повторів видалення картинки; повний первинний прогін і rerun описані в QA-звіті) виконано `docker compose up -d --wait --no-build`. Контейнер `redmine-ui-app-1` відтворено; новий контейнер (`72702797742b`) працює та має стан Docker `healthy`. Порт залишився `127.0.0.1:3010 -> 3000/tcp`. Образ використовує дайджест `76903ae078d361c5992dc4f3a0b6b542c53d295208e60ccb152daa21f9a406b2`.

До й після відтворення контейнера підключено той самий іменований том `redmine-ui_workspace-data:/data`; том не видаляли й не очищали, локальні дані збережено. Файл `.env` не редагували. Налаштування `REDMINE_URL` та ввімкнений режим запису залишилися без змін. `Config.Env` і розгорнуту конфігурацію Compose не переглядали.

Перевірки виконували лише GET-запитами. `/api/health` і `/api/bootstrap` повернули HTTP 200 та однакові дозволені метадані: `mode=redmine`, `connected=true`, `readOnly=false`, `canWrite=true`. Коренева сторінка `/` повернула HTTP 200, посилалася на `index-BvAAyVnd.js`, а запит цього файла також повернув HTTP 200.

Виводили лише HTTP-статуси, дозволені метадані та назву JS-файла; повні відповіді не друкували. Жодних змін у Redmine не виконували.
