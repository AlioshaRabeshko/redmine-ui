# UX round 5 backend report

## Contracts shipped

- `Issue.assignedToType` distinguishes `user` from `group`; `assignedToId` remains for compatibility and `assignedToName` preserves the displayed identity. `AssigneeOption` is a discriminated union with `type: 'user' | 'group'`. Group IDs are never added to user membership, watcher, Developer, or assigned-to-me logic, even when a group and user share an ID.
- `BoardData.assigneeOptions` contains users and typed groups found in fresh project memberships. Groups are not mixed into user membership, watcher, Developer, or assigned-to-me logic, even when IDs overlap. Create/update commands accept `assignedToType` plus `assignedToId`; clearing removes all assignee fields. Before a write, the executor rechecks the selected user/group against fresh project membership. Membership proves the group identity and project scope, while Redmine validates `issue_group_assignment`, assignable roles, tracker and issue permissions. A Redmine validation error is surfaced; after an accepted write the issue is reread and the requested ID/type must match.
- Redmine Developer is a compatibility alias derived only from the exact `Primary Assignee` custom field present in fresh issue data; old cached/local Developer roles are stripped during real-store reads and writes. The field must have a unique exact name and scalar value, and a catalog definition, when readable, must not contradict issue/user type, single-value shape, project or tracker applicability. If the administrator-only catalog is unavailable, the ID comes from the current issue's own custom-field payload; writes use that exact ID, rely on Redmine validation, then reread and verify the saved value. This avoids guessing IDs and does not confuse Standard Assignee with Primary Assignee.
- Per-issue transition choices travel as `Issue.allowedStatusIds` from Redmine's `allowed_statuses`. Missing data stays `undefined`; an empty list stays empty. Both disable status moves. The board receives the latest status catalog, and issues whose old status is no longer in it are consolidated into a non-droppable `status:unknown` lane so they remain accessible without offering a dead transition.
- `Filters.watcherId` filters by watcher ID. `BoardData.members` includes all known watchers, including watchers outside current project membership. `AppSettings.collapsedBoardColumns` is persisted by project ID. Subscription event settings now include `issue_created`; legacy stored event arrays are normalized to known values (deduplicated, preserving explicit empty arrays) so older unknown strings do not make settings PATCH fail.
- New-issue notifications require the issue to be absent from cache, its project to have existed in the previous project snapshot, and `created_on` to be at/after both the previous successful sync and a server-persisted per-project issue-created opt-in cursor. Enabling the event records that cutoff transactionally with settings; disabling/re-enabling records a fresh cutoff. A newly accessible project gets a quiet baseline. Legacy active subscriptions without a cutoff get one quiet sync for initialization, so deployment does not replay cached history. A failed sync does not advance the general sync cursor or consume eligible events.
- The “previous project snapshot” is the project scope persisted with the last fully successful sync, never the mutable project catalog. A partially failed sync can save projects before failing; a retry still recognizes those projects as newly re-accessible and suppresses historical discovery notifications. Successful cursor and project scope advance atomically.
- Sync merges only missing subscription defaults into the latest stored settings. Issue-created eligibility is checked transactionally at event commit against current settings and the current opt-in cutoff, so a settings PATCH that disables the event while a sync is in flight prevents the notification and records the source event as consumed. The same transactional check prevents events seen while opted out from replaying after a later opt-in.
- The real executor rejects commands before adapter calls when write mode is disabled. The public worker bridge also durably marks pending real automation records `blocked` with `READ_ONLY`, even if automation is disabled, before reading remote state. The persisted read-only marker prevents a later direct retry after re-enabling write mode; blocked automation is never automatically replayed.
- `Person.login` and `mentionToken` are separate fields. Mention tokens are emitted only from a Redmine-provided login that passes the supported token syntax; names and numeric IDs are never used to synthesize a login. Bootstrap, board, and issue detail return `textFormat` only when detected; demo explicitly returns `markdown`.
- Issue detail returns its current status catalog, detected format, and current assignee options. In real mode, journal edit/delete flags are false unless a verified capability is stored; the command executor checks the capability before requesting the issue. Like commands fail with an unsupported-capability result. For a supported journal delete, clearing the note preserves field-change details; a notes-only journal is removed by core Redmine.

## Redmine behavior checked

The official [REST issues documentation](https://www.redmine.org/projects/redmine/wiki/rest_issues) describes `allowed_statuses` as the status choices available to the current user for that issue, based on workflow, tracker, role, and other constraints; it is available from Redmine 5.0. The adapter requests this per issue and does not infer transitions from the global status list.

The official [REST journals documentation](https://www.redmine.org/projects/redmine/wiki/Rest_Journals) documents updating a journal through `PUT /journals/:id.json` with notes and requires permission to edit the user's own journal. The [REST API support table](https://www.redmine.org/projects/redmine/wiki/Rest_api/) lists Journals as available since 5.0. These references establish core behavior, but do not establish the target instance version or the current user's permission, so real journal editing and deletion remain unavailable. No official core REST endpoint for likes was found; likes remain unavailable in real mode.

The official [custom field REST documentation](https://www.redmine.org/projects/redmine/wiki/Rest_CustomFields) says definitions include type/format and that reading the catalog requires administrator access. Redmine's [custom-field documentation](https://www.redmine.org/projects/redmine/wiki/RedmineCustomFields) identifies a User custom field as a project member reference. The core [issue model](https://github.com/redmine/redmine/blob/master/app/models/issue.rb) validates assignment against `assignable_users`; the [project model](https://github.com/redmine/redmine/blob/master/app/models/project.rb) includes Group only when `Setting.issue_group_assignment` is enabled and the role/tracker permit it. The executor therefore uses membership only to validate principal identity and scope, then lets Redmine validate the actual field/workflow write and verifies the result with a fresh read.

The official [Redmine layout source](https://github.com/redmine/redmine/blob/master/app/views/layouts/base.html.erb) exposes the configured formatter in `data-text-formatting`; the [Markdown formatter documentation](https://www.redmine.org/projects/redmine/wiki/RedmineTextFormattingMarkdown) documents `@login` mentions. The adapter reads the configured formatter and only uses exact API logins for mention tokens. `common_mark` hard-break configuration is not exposed by the observed public metadata, so its value remains unknown and is not inferred.

## Read-only target-instance evidence and limits

The target configured in the running app was `https://redmine.example.com`. A backend-only probe used the existing container, explicitly set `writeEnabled: false`, and issued GET requests only. It confirmed `data-text-formatting="common_mark"` from `/login`. Issue 28692 in project 49 returned a custom field with ID 19 and the exact name `Primary Assignee`, currently empty. The admin custom-field catalog endpoint returned HTTP 403, so the actual field format, applicability, and allowed values could not be verified. The issue's `allowed_statuses` response was empty; the adapter preserves that empty list. `/admin/info` did not reveal the Redmine version.

The follow-up GET to `/issues/28692/edit` returned the login form rather than an issue form, so it could not verify field widget markers or assignable group choices. No browser-session credentials were read or requested. The issue API itself confirmed the unique field ID 19 and exact name `Primary Assignee`; the catalog endpoint's HTTP 403 leaves the field format, multiplicity/applicability metadata and option widget unverified. The backend now uses that exact fresh issue-field ID, validates the chosen user against fresh project membership, and verifies the result after Redmine accepts a write. It does not guess a field ID or treat Standard Assignee as equivalent; whether this target field is configured as Redmine's User format remains unverified. Group choices come from fresh project membership, but actual assignment depends on Redmine's setting and permissions and may return a validation error. Real own-journal edit/delete remain disabled because the instance version and capability are unverified; journal likes remain unsupported. No Redmine, Trello, or production database mutations were performed.
