# Повторний UX аудит: висновки за кодом — 2026-10-04

Це read-only аудит UI, state та API форми. Перевірено `AGENTS.md`, `RESEARCH.md` §§19.16–19.26, `REVIEW.md`, `TECHNICAL.md` і вимоги з `docs/UX_ROUND2.md`. Код, налаштування, тести й Git не змінювалися; браузер і сервер не запускав, `.env` не читав, зовнішніх запитів на запис не виконував. Браузерні спостереження мають лишитися окремо у звіті іншого агента.

## Підтверджені причини

1. **Горизонтальний скрол усередині колонки блокує межа вкладеного скролу.** `src/client/styles.css:130` задає дошці `overflow-x: auto`, `overflow-y: hidden`, `overscroll-behavior: contain`; `:151` задає `.lane-content` вертикальний скрол і той самий `contain` без осьового обмеження. `contain` на внутрішньому контейнері ізолює обидві осі, тому жест над картками не переходить до дошки. Конкретну поведінку wheel/trackpad має підтвердити браузерний аудит. Висота коротких колонок випливає з `.board-lanes { align-items: stretch }`, `.board-lane { height: 100% }` та `.lane-content { flex: 1 }` (`:137–152`); dropzone ще й має `min-height: 100%`. Ці правила розтягують і короткий вміст на всю висоту дошки. Колонковий scroll та DnD dropzone (`BoardPage.tsx:112–116`) треба зберегти при зміні висоти.

2. **Вибраний assignee накладає круглу рамку на рольову рамку іншої форми.** `IssueDialog.tsx:583–585` використовує `.assignee-avatar-option`; `styles.css:376–378` завжди робить її круглою й додає selection border плюс зовнішній box-shadow. Внутрішній `.avatar` має форму ролі: developer — округлий квадрат, QA — коло, support — восьмикутник (`styles.css:275–281`). Для developer/support геометрії не збігаються; це конкретна причина «кривої подвійної рамки», яку можна виправити, прив'язавши selection indicator до форми аватара або винісши його окремо без накладання.

3. **Журнали не сортуються нові спершу.** `WorkspaceStore.getJournals()` повертає `createdOn ASC` (`src/server/db/store.ts:250–253`); свіжі журнали з real detail мапляться у порядку відповіді без сортування (`src/server/redmine/adapter.ts:225–247`). `visibleJournals()` зберігає вхідний порядок (`src/client/lib/issueActivity.ts:32–47`), а `IssueDialog.tsx:529` його рендерить. Сортувати варто копію списку за `createdOn DESC`, з `id DESC` для рівних timestamp; не мутувати кешований масив. Permalink шукає journal за ID, а потім прокручує до його DOM id (`IssueDialog.tsx:217–224`), тож треба зберегти цей зв’язок після сортування.

4. **Activity вже налаштовується per-project, але з картки змінити фільтр не можна.** `defaultActivityVisibility` — comment/status/assignee увімкнені, labels/field вимкнені (`src/shared/types.ts:15–17`). Налаштування зберігається в `AppSettings.projectActivity`, сервер зливає лише вказаний project (`src/server/settings.ts:47–55, 116–122`), Settings autosave використовує поточний проєкт (`SettingsPage.tsx:186–189, 381–384`), а `App.tsx:607` передає цей project’s state у `IssueDialog`. `visibleJournals()` окремо фільтрує note і кожну зміну; permalink тимчасово показує свій target, не переписуючи preference (`issueActivity.ts:32–47`). Для режиму «лише коментарі» достатньо вже наявної моделі — у картці бракує inline-контролу. За уточненням root, він має змінювати й autosave-ити те саме project-wide `projectActivity`, а не локальний transient стан однієї картки.

5. **Priority pills мають слабку візуальну виразність на світлій дошці.** `styles.css:175–176` використовує тонкий контур із 36% кольору, заливку з 8% та різні приглушені foreground colors; картка рендерить це як компактну плашку з іконкою й назвою (`BoardPage.tsx:69–72`). Це пояснює скаргу на помітність. У цьому аудиті числової WCAG-помилки не встановлював: факт попереднього проходження тестів текстового контрасту не доводить достатньої помітності плашки та рівнів пріоритету.

6. **У діалозі статус і пріоритет повторюють editable поля справа.** У модальному eyebrow статус уже входить після tracker (`IssueDialog.tsx:498`), toolbar має status pill і priority text (`:499–504`), а sidebar містить status picker і priority tiles (`:578–582`). Для видалення дубля треба врахувати обидва верхні статусні місця, а не лише pill.

7. **Inbox — плоский список окремих notification events.** `InboxPage.tsx:10–17` сортує рядки за `notification.createdOn DESC`, групування за issue відсутнє; кожен рядок має власні journal/issue IDs (`:20–30`). API віддає unread і archived окремими списками за `readAt` (`src/server/db/store.ts:322–325`); dedup уже відбувається за source event `journal:<id>` (`sync/service.ts:175–204`, `store.ts:355–367`). Клік конкретної події відкриває її `journalId` і позначає лише її прочитаною (`src/client/app/App.tsx:486–502`). Майбутню групу треба будувати з цих events: показувати новішу подію першою, сортувати групу за найбільшим `createdOn` її notification, а read/archived стан зберігати на кожному event ID. Розкриття/згортання групи не має викликати `markRead`; групова дія «прочитати всі» може передавати лише фактичні event IDs. Це не потребує використовувати `Issue.updatedOn`.

8. **Джерело project roles вже є; дані губляться під час проєкції людей.** Redmine adapter читає `/projects/:id/memberships.json`, зберігає project-specific member IDs та role arrays (`src/server/redmine/adapter.ts:81–88, 133–149`). Board endpoint накладає мапінг Redmine roles і local override на `members` (`src/server/app.ts:175–189`). Проте mapping у `app.ts:465–475` розпізнає лише кілька англомовних назв ролей; невідомі назви залишаються в `redmineRoles`, але не потрапляють до QA/support/developer `roles`. Це обмеження класифікації, а не доказ відсутності membership role.

   Detail endpoint повертає `watchers` із глобального `people` та `people` з Redmine detail без project enrichment (`app.ts:265–297`). Далі `IssueDialog.tsx:156–157` зливає `board.members`, `detail.people` і `journal.user` у Map із last-wins: сирі detail/journal записи можуть перезаписати project-enriched board member. Watchers окремо малюються прямо з `detail.watchers` (`IssueDialog.tsx:595–597`). У notification ingestion actor береться зі звичайного `snapshot.people`, а GET notifications повертає збережений payload без project-role lookup (`sync/service.ts:200–203`, `app.ts:390`); тому notification Avatar не має ролей.

   Root повідомив підтвердження з read-only GET preview: 17 подій на 8 задачах, 4 задачі з кількома подіями, жоден notification actor не мав `roles`; для #issue-example author у `board.members` має `roles=['qa']`, але `detail.people` повертає його без `roles`; 4 watchers, 0 із `roles`. Це підтверджує втрату саме в data shape. Ще один кодовий дефект: local override дозволяється Settings UI для людини зі списку `members`, але board projection перед override робить ранній return, якщо ID відсутній у Redmine `membershipIds` (`app.ts:183–188`); explicit local override для такого учасника ігнорується. При виправленні спочатку застосовувати project-scoped override, коли він заданий; інакше успадковувати наявні Redmine roles. Проєкція має бути єдиною для board members, issue detail people/watchers/journal actors та notification actor за `projectId`, без перенесення ролей з іншого проєкту.

9. **Аватари показують лише одну літеру для login-style імен, і локальних override немає.** `Avatar` в `src/client/components/ui.tsx:8–19` бере перші символи максимум двох слів; `example-user-a` дає одну літеру. Redmine avatar URL підтримується адаптером (`src/server/redmine/adapter.ts:364–366`), але окремого app-local person icon немає. SQLite settings scope формується як Redmine instance + поточний user ID (`src/server/sync/service.ts:48–51`; `config.ts:62`); байтове зберігання для project backgrounds уже відділене від settings map і доступне через локальний API (`src/server/db/store.ts:97–112`, `app.ts:441–462`). Пропонована межа: override кожної людини зберігати в локальному instance/user scope і застосовувати в усіх проєктах цього користувача; project-specific лишаються тільки role frames. Метадані/URL — у settings map, зображення — окремими обмеженими байтами на зразок background. Не вкладати base64 у bootstrap. Для initials використовувати два Unicode grapheme clusters для однословного імені та лишити зрозуміле правило для повного імені. Персональне фото має бути локальним, без Redmine/Trello upload.

10. **Read-only показаний у sidebar і великих постійних Notice, але відсутній як topbar state.** Topbar connection pill повідомляє лише Connected/Offline (`src/client/app/App.tsx:589–595`); mode/read-only є у sidebar footer, який ховається при collapsed sidebar (`:586`, `styles.css:71–75`). Великі Notice є в дошці, Issue/Create dialogs, Settings, Releases і Operations drawer (`BoardPage.tsx:232`, `IssueDialog.tsx:511,669`, `SettingsPage.tsx:331`, `ReleasesPage.tsx:131`, `App.tsx:654`). Модальний backdrop перекриває topbar (`styles.css:204`), тому для критерію «видно й з відкритою карткою» потрібен compact state також у видимому modal header/toolbar або інший перевірений спосіб не закривати indicator. Form inputs disabled коли `canWrite=false`; description/comment drafts пишуться в `localStorage` за instance/user/issue/field, а блокування має окреме повідомлення. `runCommand` відхиляє запис до command request (`App.tsx:303–315`); цю безпеку та збереження чернеток лишити.

## План майбутнього виправлення та приймання

- **Board scroll/height:** дозволити горизонтальний scroll chaining із lane до board, залишивши вертикальне containment; коротка/порожня колонка має природну висоту, довга — обмежену видимою областю карток із власним vertical scroll. Порожня колонка має заголовок, create control і достатню drop area. Trackpad горизонтально над карткою рухає board, вертикально — колонку; DnD autoscroll працює в обох напрямках. Не перехоплювати всі wheel-події JS-ом без потреби.
- **Assignee geometry:** у selected avatar немає подвійних рамок, що перетинаються; рамка/індикатор selection узгоджується з developer square, QA circle, support clipped frame та multi-role marker, не змінюючи зовнішній hit target. Зберегти visible/accessible selected state.
- **Activity/journal:** Activity control у відкритій картці оновлює і autosave-ить project-wide `projectActivity`; category toggles дозволяють лишити тільки comments. Відкриття іншої картки того ж проєкту показує те саме налаштування; інший проєкт не змінюється; локальна підписка inbox і unread state не змінюються. Події newest-first із часовим tie-break `journal.id DESC`; permalink і його reveal для прихованого типу, quote/edit/delete та keyboard focus і далі ведуть на той самий journal.
- **Priority/header:** у light board плашка пріоритету одразу помітна як текстом, так і контуром/фоном, рівні розрізнюються без збільшення всіх шрифтів; оцінити реальний вигляд у light/dark і палітрах, окремо рахувати text contrast і non-text boundaries. Верхній IssueDialog прибирає дубль status/priority; editable значення лишається справа.
- **Inbox/roles:** inbox відображає одну групу на issue ID, групи сортуються за часом найновішої notification, події всередині — newest-first. Expand не змінює read state; відкриття конкретної події фокусує відповідний `#change-<journalId>` і архівує лише її; mark-all діє на event IDs; unread badge/favicon та archive/unread lists узгоджені. Actors, authors, assignees, watchers і journal users отримують ролі тільки з membership відповідного project плюс його local override; не-член із явним override не втрачає його; сирий `Person` не перезаписує enriched record. Multiple roles зберігаються в доступному label/title, frame selection стабільна.
- **Avatar/read-only:** однословне ім’я дає два коректні Unicode символи; local icon людини переживає reload, зміну проєкту й restart, але ізольований між Redmine instance/current user; його можна замінити/скинути без зовнішнього запису. Компактний warning topbar постійно позначає тимчасовий read-only; стан лишається помітним зі згорнутим sidebar і при відкритій картці. Він пояснює, що дії в Redmine тимчасово заблоковані, а налаштування й чернетки локальні. Будь-яка заблокована дія завершується без зовнішнього запиту, не втрачає drafts; локальні settings і notification read/archive продовжують працювати.

## Ризики й межі наступної перевірки

- Переміщення ролей між Settings/UI cache може показати stale override під час autosave або зміни проєкту; merge має бути keyed by `projectId/personId` і враховувати explicit override над успадкованими Redmine roles.
- Activity toggles і autosave можуть конкурувати з іншими settings; використовувати чинні patch merge/rollback й поле актуального `settingsRef`, не перезаписувати решту project visibility. Shortcut drafts лишаються окремими явними drafts.
- Inbox grouping не має зливати event IDs чи відмічати все issue прочитаним. Перевірити одночасні Mark all, refetch/focus, unread cache/favicon, archive/unarchive та duplicate source events. Групове сортування спирається на notification `createdOn`; окремого узгодження використовувати Redmine `updatedOn` немає.
- Local icons — user-scoped локальні дані; ліміт bytes/MIME, failed-image fallback, clear/revert, asset cleanup і відсутність base64 у bootstrap мають бути визначені до реалізації. Не дозволяти локальній іконці змінювати role frame.
- Перевірити contrast чисельно лише для зафіксованих foreground/background станів; попередній текстовий WCAG pass не закриває visual prominence. Mobile повний аудит відкладений.

Під час цього аудиту unit/E2E/build тести не запускав: змін коду не було, а браузерна перевірка делегована окремо.
