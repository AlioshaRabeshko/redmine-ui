# Аудит форматування та швидкості відкриття задачі

Це read-only аудит після паузи в реалізації. Переглянуто надані знімки екрана, вихідний код і наявні файли `dist`. Код, стилі, залежності, тести й конфігурацію не змінював; тести, браузер, сервер і збірку не запускав. `.env`, облікові дані та зовнішні API не читав і не викликав.

## Preview опису та форматування коментарів

У наданому порівнянні Preview показує великі порожні проміжки навколо цитати й між пунктами списку; VisualEditor показує той самий видимий текст компактно. Це візуально підтверджує розбіжність, але не визначає точну структуру збереженої розмітки.

Найсильніша підказка в коді — `.description-preview { white-space: pre-wrap }` у `src/client/styles.css:240`. Усередині цього контейнера стоїть `RichContent` (`src/client/features/issues/IssueDialog.tsx:875-877`), а його кореневий `.rich-content` не задає власний `white-space` (`src/client/components/RichContent.css:1-7`). Тож режим збереження пробілів успадковується Markdown-вузлами. Це узгоджується зі знімком і є ймовірним джерелом зайвих переносів. Правила Markdown-блоків задають звичайні відступи лише `7px` (`RichContent.css:11-16`), тому самі вони не пояснюють такі великі проміжки. Без інспекції DOM і обчислених стилів точну причину ще не підтверджено: можливі також структура отриманого HTML та правила для вкладених блоків.

Коментарі користуються тим самим `RichContent` і тим самим `ReactMarkdown` ланцюжком (`IssueDialog.tsx:934`, `RichContent.tsx:377-401`), але на них впливають інші зовнішні правила. Селектори `.activity-body p`, `.activity-body ul` та `.activity-body li` у `src/client/styles.css:241` охоплюють і розмітку коментаря: параграфам задають `white-space: pre-wrap`, спискам `<ul>` — `list-style: none`, а елементам `<li>` — `display: flex`. Це правила для рядків змін журналу; через широкий селектор вони можуть змінити переноси й вигляд списків у тексті коментаря. Знімок наданого коментаря не містить видимого списку, тож поведінку списку в коментарі ним не перевірити. Тут є окреме від Preview питання CSS scope, хоча renderer спільний.

Наявні перевірки підтверджують семантичне відображення цитат, списків, коду й безпечного HTML (`src/client/components/RichContent.test.tsx`, `e2e/round5-editor.spec.ts:143-188,246-289`), але не перевіряють обчислений `white-space`, розмір вертикальних проміжків чи списки всередині Activity. Раніше погоджений режим CommonMark не перетворює одиночний перенос рядка на `<br>` без підтвердження відповідного налаштування Redmine; це зафіксовано в `docs/UX_ROUND5_EDITOR.md`. Подальша перевірка має окремо порівняти `white-space` і вертикальні відступи Preview та Activity, а стилі для рядків змін журналу обмежити самим списком змін.

## Затримка відкриття

Відкриття задачі має щонайменше два послідовні клієнтські очікування до появи діалогу. Ефект у `src/client/app/App.tsx:497-515` чекає на завантаження detail, потім на `fetchQuery` дошки цільового проєкту і лише після цього встановлює `freshIssueDetailId`. Сам `IssueDialog` відображається через `React.lazy` під `Suspense` (`App.tsx:23,1118-1121`), тому завантаження його модуля починається після цієї умови. Коли дошка застаріла або проєкт відкривається вперше, очікування дошки може відкласти показ задачі. Це висновок з порядку коду, а не вимірювання мережевого часу.

Наявний на диску знімок `dist/client/assets/IssueDialog-CMhMTGKP.js` має **1,058,376 байтів**; standalone gzip для цього файла — **323,711 байтів**. Основний `index`-файл має **611,464 байти** (**180,524** після standalone gzip), а CSS чанка діалогу — **6,833 байти**. Це розмір наявних артефактів, не нової збірки й не фактичний розмір HTTP-відповіді: сервер може застосувати інше стиснення. Попереднього чанка для порівняння немає, тому приріст від UX5 не встановлений.

Діалог статично імпортує `RichEditor` (`src/client/features/issues/IssueDialog.tsx:10`), а редактор імпортує Tiptap та Markdown extension (`src/client/components/RichEditor.tsx:1-10`). Він монтується в composer коментаря одразу (`IssueDialog.tsx:891-894`), навіть коли опис за замовчуванням відкритий у Preview (`:875-877`). Отже важка логіка редактора входить до чанка, потрібного для першого відкриття задачі. Лише `React.lazy` без відкладеного монтування editor-компонента може все одно почати завантажувати редактор відразу, бо composer уже присутній у дереві. Також обидва lazy-entry — `IssueDialog` і `CreateIssueDialog` — імпортують той самий модуль (`App.tsx:23-24`), що варто врахувати при майбутньому поділі чанка.

Для підсвічування `RichContent.tsx:3,398` використовує `rehype-highlight` з `detect: false`. Локальна реалізація `rehype-highlight` за замовчуванням реєструє `lowlight` `common`; у встановленому пакеті це 37 граматик (`node_modules/lowlight/lib/common.js`). Тож це не всі мови highlight.js, хоча цей набір також потрапляє до чанка діалогу. Явні, але незареєстровані мови лишаються читабельним кодом — саме це перевіряє `RichContent.test.tsx:114-118`; вони не обов'язково отримують підсвічування. Оптимізація має зберегти підтримку потрібних мов та псевдонімів; твердження, що тепер завантажуються всі мови highlight.js, джерелами не підтверджується.

Наступний крок для вимірювання — записати мережевий waterfall і часи трьох етапів: `/api/issues/:id`, `/api/projects/:id/board`, завантаження чанка діалогу, окремо для першого та повторного відкриття. Так стане зрозуміло, який етап домінує. Кандидати для наступного виправлення: запуск імпорту діалогу паралельно з detail/board-запитами, показ shell діалогу до завершення другорядного завантаження дошки, а також відкладене монтування RichEditor до входу composer у видиму область або фокусу користувача. Ці варіанти тут не реалізовані й потребують перевірки збереження фокусу та чернеток. Детальніше джерельне дерево backend-запитів зафіксує окрема нотатка аудиту задачі.

## Збережені фрагменти, зображення та межі WYSIWYG

Напис «Збережений вміст — редагуйте в режимі розмітки» точно описує нинішню поведінку зображень у візуальному редакторі. Редактор не має image extension або кнопки вставлення зображення: у `RichEditor.tsx:139-143` підключені StarterKit, Markdown і atom для збереженого source; toolbar у `:271-285` містить форматування, код, списки, цитату та посилання, але не зображення. `Source` відкриває контрольоване textarea з повним сирим текстом (`:287-303`).

Візуальний режим за замовчуванням готує source з `protectImages: true` (`redmineFormatting.ts:284-294`). Наявний фрагмент зображення стає атомом, який не можна редагувати всередині canvas: `redminePreserved` — `atom: true`, `selectable: true` (`RichEditor.tsx:23-30`), а його NodeView має `contentEditable={false}` (`:15-20`). Canvas показує один загальний pill із текстом «Збережений вміст — редагуйте в режимі розмітки»; повний raw source доступний у `title` і в режимі Source. Label, який formatter обчислює для зображення, не показується: `PreservedSourceView` читає `raw`, але не `label`. Тобто існуюче зображення зберігається під час редагування сусіднього тексту, однак у WYSIWYG його не видно як картинку, його атрибути не редагуються, і вставити нове зображення через toolbar не можна. Preview використовує інший шлях (`protectImages: false` у `redmineFormatting.ts:344-356`) і може відобразити підтримуване зображення через `RichContent` та issue-scoped resolver.

Поточні правила утворення opaque-атомів мають такий обсяг:

| Source | Поведінка в VisualEditor | Preview / межа |
| --- | --- | --- |
| Markdown inline image `![alt](url)` | Один збережений атом; для редагування URL/alt потрібен Source. | Markdown Preview може рендерити його через `RichContent`. |
| Markdown reference image/link, footnote references та definitions | References і рядки definitions стають атомами; їхню ціль чи вміст не можна редагувати в canvas. | Formatter відновлює source перед Preview, де parser обробляє підтримувану форму. |
| Raw HTML, зокрема `<img>` | HTML-теги стають атомами; `script/style/iframe/object` фрагменти зберігаються цілком. | Preview санітизує дозволений HTML; активні/небезпечні елементи не стають активними. |
| Textile `!…!` image | Один збережений атом; зображення не відображається в canvas. | Preview перетворює підтриманий Textile image source на зображення через той самий resolver. |
| Markdown/CommonMark table та task list | Таблиця з заголовком і розділювачем або послідовні рядки з checkbox зберігаються як атом; клітинки й прапорці не редагуються візуально. | Preview може відобразити їх через GFM renderer. |
| Textile table, наявні `bc.`/`pre.` чи fenced code, `<pre>`, `bq..`, `notextile.`, Redmine macros і raw HTML | Таблиця або весь відповідний block/macro захищається як атом. Звичайні заголовки, списки та підтриманий inline текст лишаються редагованими. | Частина конструкцій, як-от `bq..` і код, має окреме перетворення для Preview; це не означає, що її можна редагувати в canvas. |
| Markdown fenced code | Не стає opaque-атомом для CommonMark/Markdown; StarterKit дає code-block для візуального редагування. | Для Textile збережені наявні code blocks opaque за замовчуванням; нові code blocks із toolbar серіалізуються в Redmine `<pre><code>` (`redmineFormatting.ts:215-238,248-295,320-341`). |

Джерельні перевірки підтверджують збереження reference images/links і definitions та повних Markdown table/task-list блоків при зміні сусіднього тексту (`redmineFormatting.test.ts:44-76`). `RichContent.test.tsx:109-112` підтверджує відображення Textile image в preview. Це перевірки formatter/renderer, а не браузерна оцінка того, наскільки зрозумілим або придатним до роботи є pill.

Отже це частковий WYSIWYG з безпечним збереженням невідомих/складних source-конструкцій. Якщо очікування — бачити існуючу картинку та змінювати її alt/URL без Source, нинішній редактор цього не підтримує. Для такого результату потрібні окремий image node/preview і image toolbar з контрольованою серіалізацією для підтверджених форматів. Як малий UX-крок можна показувати на pill його наявний `label` (наприклад, назву зображення або тип збереженого блоку), але це не замінить перегляд чи редагування картинки. Жодна з цих змін не реалізована в межах аудиту.

## Межі висновків

- Жодного browser timing, DOM inspection, мережевого waterfall чи HTTP-запиту в цьому аудиті немає.
- Розмір `dist` — лише локальний знімок наявних артефактів; збірка не запускалась.
- Збережена розмітка конкретної задачі та коментаря не отримувалась. Припущення про неї не робляться.
- Рекомендації вище не є реалізованими змінами.
