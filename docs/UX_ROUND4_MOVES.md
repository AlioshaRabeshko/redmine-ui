# Оптимістичне переміщення карток

Після drop картка негайно показується у цільовому статусі та з ознакою збереження. Команда лишається заблокованою для цієї картки, доки підтвердження Redmine не узгоджене з локальним кешем. Запит скасовує попередні board-запити, а підтверджений стан захищає картку від застарілих відповідей SSE і polling.

За однозначної відмови застосунок перечитує задачу й показує її фактичний стан. Після часткового або невизначеного результату він також читає Redmine, показує фактичний status/version і не надсилає компенсувальних команд. Якщо читання тимчасово недоступне, картка лишається у стані перевірки; повторюється тільки GET із затримкою до 30 секунд. Перевірена відповідь 403/404 прибирає недоступну картку й повідомляє про це.

Рух між статусами й належність до релізу лишаються незалежними: drop Deploy-задачі в реліз змінює Version, не статус; інші статуси не переписуються через зміну членства. Одночасні зміни різних карток працюють незалежно, а повторний рух картки під час збереження вимкнений. Швидка дія беклогу «У To Do» використовує той самий шлях.

Для непрочитаних подій звичайне відкриття задачі відмічає лише ті події поточного issue, які були видимі й не приховані фільтрами. Автоматичне та явне прочитання ділять один API acknowledgement; локальний стан оновлюється лише після успіху API.

Перевірено: `npx tsc --noEmit`, `npx vitest run src/client/lib/optimisticIssueMove.test.ts` (9 тестів) і `npm run test:e2e -- e2e/round4-moves.spec.ts` (4 сценарії проти demo fixtures та mock routes).
