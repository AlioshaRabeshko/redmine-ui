# Подальший аудит Round 5: аватари груп і backend-завантаження задачі

Це лише аудиторська нотатка. У ній зафіксовано докази з коду та обмежені рекомендації; реалізацію й тести не змінено.

## Фото й emoji груп налаштувати неможливо

Наявна функція локальних аватарів призначена лише для людей:

- `PersonAvatarOverride` підтримує фото й emoji, а `AppSettings.personAvatarOverrides` має тип `Record<string, PersonAvatarOverride>` з числовим ID людини у ключі (`src/shared/types.ts:10,17,50-69`). Сервер перевіряє ці ключі та URL фото як ID людини (`src/server/settings.ts:13,23-36`).
- Settings вибирає `rolePersonId` зі списку `members: Person[]`, а контролли аватара з'являються лише після знаходження відповідного `Person` (`src/client/features/settings/SettingsPage.tsx:112-159,415-425,513-558`). У `App.tsx:1114` передається `board.members`, але типізовані варіанти груп не передаються.
- Завантаження, читання й очищення використовують `/api/people/:id/avatar`. Під час завантаження сервер перевіряє, чи є цей числовий ID у кешованому масиві `people` (`src/server/app.ts:154-169`; читання й видалення — у `172-197`). У Redmine ID групи може збігатися з ID людини. Тому повторне використання цього маршруту чи мапи для групи звернулося б до аватара людини та могло б його перезаписати. Тип сутності має залишатися частиною ключа сховища й маршруту; групу не можна передавати як `Person`, у `projectPerson` або в `/api/people/:id/avatar`.
- Призначення виконавця вже типізоване: `AssigneeOption` розрізняє `user` і `group`, а picker використовує ключі `user:<id>`/`group:<id>` (`src/shared/types.ts:18-20`; `src/client/components/pickers.tsx:130-169`). Зараз групи всюди позначені загальною піктограмою Users (`pickers.tsx:154-159`, `IssueDialog.tsx:970`, `BoardPage.tsx:90`, `BacklogList.tsx:60`). Через це фото й emoji групи ніде налаштувати або показати.

### Рекомендований підхід

Ідентичність групи слід відокремити від людей, водночас повторно використавши наявний механізм локальних фото:

1. Додати до налаштувань мапу `groupAvatarOverrides` з ключем Redmine group ID і таким самим форматом фото або одного emoji. Вона має бути окремою від `personAvatarOverrides`: самого числа недостатньо для визначення типу сутності. Налаштування варто зберігати в поточній області інстансу Redmine і користувача, як і локальні аватари людей, щоб одна група мала однаковий вигляд у різних проєктах цього облікового запису.
2. Зберігати байти зображень за окремим ключем групи. Наявне сховище тримає байти фото у записах із ключами на кшталт `personAvatar:<id>` (`src/server/db/store.ts:122-146`); для груп підійде окремий ключ `groupAvatar:<id>`. Окрема таблиця не потрібна, доки майбутні потреби у сховищі цього не виправдають. Додати маршрути завантаження, читання й видалення `/api/groups/:id/avatar`, використовуючи чинну перевірку растрового формату, версійний URL, обмеження розміру та очищення застарілої версії. Перевірка запису має підтверджувати, що ID відомий як група з даних про membership проєктів Redmine, а не як людина. Збіг ID з користувачем не повинен впливати на його аватар.
3. Передавати до Settings типізовані варіанти груп окремо від `members`, використовуючи групи поточного проєкту або відомі групи інстансу. Додати вибір групи й перевикористати контролли фото та emoji зі станом і маршрутами для груп. Не додавати групи до `PeoplePicker`: локальні ролі, QA, рекомендації та ролі з membership призначені лише для людей.
4. Додати компонент `GroupAvatar`, який приймає ідентичність групи, показує її локальне фото чи emoji, а за відсутності налаштування — чинну піктограму Users. Використовувати його для призначених груп на дошці, у Backlog, деталях задачі та assignee picker. Компонент `Avatar` і рамки ролей залишити лише для людей. Під час кожного відображення й збереження зберігати `type: 'group'`, навіть коли ID групи збігається з ID користувача.

Поточний список груп походить із membership проєкту (`src/server/app.ts:238,247-252`; `src/server/redmine/adapter.ts:182-199`). Як перший крок Settings може показувати відомі групи активного проєкту, а сам override зберігати в області користувача й інстансу, щоб та сама група зберігала вигляд в інших проєктах.

## Регресія завантаження задачі на backend: граф запитів і причини

Виміряти час у поточному runtime з цього workspace не вдалося: sandbox заборонив обмежений GET до `http://127.0.0.1:3010/api/health` (`PermissionError: Operation not permitted`). Інтерфейс задачі та endpoint задачі я не відкривав, тому вимірювань реального сервера немає. Наведений нижче висновок ґрунтується на поточному коді та порівнянні з tracked `HEAD`.

### Теплий запит `GET /api/issues/:id` за вже встановленого з'єднання

Перш ніж повернути деталі задачі, `src/server/app.ts:343-367` очікує на завершення такої роботи:

1. `adapter.issueDetail()` спершу запитує свіжу задачу з журналами, спостерігачами, вкладеннями й дозволеними статусами (`src/server/redmine/adapter.ts:293-316`). Це безпосереднє читання задачі існувало до Round 5.
2. Тепер метод безумовно викликає `readCustomFieldCatalog()` для пошуку `Primary Assignee` (`adapter.ts:313`). Якщо кеш Labels порожній, а задача має поля labels/tags, перед цим `issueDetail()` уже викликає `readCustomFieldDefinitions()` у `304-310`; цей helper також запитує той самий каталог. Отже, за одне відкриття `/custom_fields.json` може запитуватися двічі. У `HEAD` каталог читався лише умовно — для розв'язання labels/tags за відсутнього кешу; безумовне читання каталогу при кожному відкритті для `Primary Assignee` з'явилося тепер (`git show HEAD:src/server/redmine/adapter.ts`, старий метод приблизно на рядках 212-230).
3. Далі handler очікує на `adapter.issueAssigneeOptions()` (`app.ts:366`). Цей метод повторно запитує сторінки membership проєкту та завантажує відомості про кожну групу через `groups/:id.json?include=users` (`adapter.ts:343-352,450-469`). Запити виконуються щоразу при відкритті задачі. `projectGroupIds` зберігає лише множину ID для визначення типу групи, а не результати membership чи доповнені відомості про групи. Запити груп виконуються максимум по три паралельно. Помилки перехоплюються, але handler усе одно чекає завершення запитів.
4. `issueDetail()` також може запитати до 12 користувачів, згаданих у старих журналах (`adapter.ts:319-335`), а за відсутності варіантів labels — завантажити допоміжні HTML-сторінки форми/задачі (`304-310`, `569-582`). Ці необов'язкові запити для журналів і форм існували до Round 5; це не основна нова причина затримки.

Diff маршруту підтверджує, що отримання `remoteAssigneeOptions` у критичному шляху відповіді додано нещодавно (`src/server/app.ts:348-367`; порівняйте колишній handler у `git show HEAD:src/server/app.ts`). На клієнті вже використовується `detail.assigneeOptions ?? board.assigneeOptions` (`src/client/features/issues/IssueDialog.tsx:258`), тож для відображення наявного picker не потрібен новий мережевий запит при кожному відкритті. Перед записом executor окремо повторно перевіряє вибраного користувача чи групу за свіжим membership, як вимагають `docs/UX_ROUND5_BACKEND.md` і `src/server/commands/real-executor.ts`.

### Холодний старт або від'єднаний backend

Цей самий маршрут спершу очікує на `sync.bootstrapRead()` (`app.ts:344`). Якщо backend ще не під'єднаний, цей виклик очікує завершення повної початкової синхронізації (`src/server/sync/service.ts:26-34,49-64`). У такому випадку діалог задачі чекає на проєктну синхронізацію до власного запиту деталей задачі.

У Round 5 до цієї синхронізації додано такі очікувані запити метаданих:

- По одному `groups/:id.json?include=users` для кожної групи в membership кожного проєкту; максимум три паралельно (`adapter.ts:182-199`).
- Найкращі зусилля для пошуку кожного унікального ID `Primary Assignee`, відсутнього в мапі людей; максимум чотири паралельно (`adapter.ts:246-276`).
- HTML-запит до `/login`, щоб визначити формат тексту інстансу (`adapter.ts:279,546-551`).

Базові запити проєктів, статусів, пріоритетів і завантаження списку/деталей задач уже були в попередній версії. `/custom_fields.json` також уже запитувався один раз у `snapshot()` через `readCustomFieldDefinitions()`; Round 5 розширив склад полів у каталозі, але не додав ще один виклик каталогу на рівні синхронізації. Чіткі нові причини для теплого шляху — безумовне читання каталогу та повторні запити membership і груп при відкритті задачі. На холодному шляху новими є доповнення даних груп, пошук відсутніх користувачів `Primary Assignee` і запит формату.

### Рекомендації для подальшої реалізації

- Прибрати повторні мережеві операції з критичного шляху відповіді задачі: використовувати вже завантажені `assigneeOptions` з дошки або обмежений кеш/single-flight для membership і назв груп за проєктом. Зберегти свіжу перевірку membership і прав перед записом у реальному executor; кеш клієнта не повинен давати право на запис.
- Визначати `Primary Assignee` за метаданими, завантаженими один раз під час синхронізації, або за унікальним точним полем у відповіді задачі, зберігаючи наявні fail-closed перевірки. Не запитувати каталог адміністратора при кожному відкритті деталей. Якщо Redmine забороняє доступ до метаданих, залишати чесне порожнє/невідоме значення.
- Розглядати доповнення `memberIds` для груп як необов'язкове, якщо жодна видима функція його не використовує: клієнт зараз показує лише значок групи й назву. Якщо ці дані потрібні, кешувати їх і оновлювати поза шляхом відповіді деталей окремої задачі.
- Якщо є безпечне кешоване значення, винести формат тексту й пошук відсутніх користувачів із критичного шляху першого відкриття діалогу. Інакше спершу показати задачу з неповними необов'язковими метаданими й дозавантажити їх після відповіді. Не послаблювати свіжість основних даних задачі й не приховувати справжні помилки Redmine.
- Перед подальшою оптимізацією додати безпечне вимірювання часу й кількості запитів окремо для маршрутів та класів endpoint-ів Redmine. Записувати лише назви маршрутів, класи endpoint-ів, кількість, тривалість і HTTP-статуси; не записувати текст задач, персональні дані, payload відповідей, токени чи повний об'єкт bootstrap.

Точна затримка в production і частота повільних відповідей або HTTP 403 від endpoint-ів custom fields і Groups залишаються неперевіреними. Аналіз коду доводить наявність додаткових очікуваних запитів, але не їхню фактичну тривалість на цільовому Redmine.
