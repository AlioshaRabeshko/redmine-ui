# Повне рев'ю ресерчу Redmine UI

Дата: 2026-10-01, Asia/Tbilisi. Документ: [RESEARCH.md](RESEARCH.md).

Обсяг і критерії актуалізовано 2026-10-02 за відповідями користувача: чеклісти відкладені, Agile-доповнення відхилені; погоджені ручний вибір розробника, обидва способи прочитання й показ усіх задач у складі релізу. Знахідки нижче зберігають контекст рев'ю від 2026-10-01 із позначенням зміненого обсягу.

Після обговорення призначення Done користувач погодив автоматичне закриття задач при завершенні релізу без колонки Done чи додаткового ручного кроку; див. [розділ 14.3 RESEARCH.md](RESEARCH.md#143-уточнення-поведінки-після-ревю). Закритий статус фактичного інстансу потребує перевірки, назви Done недостатньо. Технічні пропозиції для наступного обговорення — [TECHNICAL.md](TECHNICAL.md), конкретний стек ще не погоджено.

## 1. Висновок і межі перевірки

Ресерч достатній для проєктування погодженого продукту, але ще не є перевіреною специфікацією інтеграції. Найбільша невизначеність — API конкретного Redmine та джерело ролей розробника / QA; ручний вибір невідомого розробника погоджено. Сховище чеклістів більше не є залежністю поточної реалізації. Обіцянки атомарності, exactly-once виконання й автоматичного відновлення будь-якої помилки були б передчасними.

Звірено всі тематичні розділи й журнал з відповідями користувача: локальний Docker, сортування, подання й фільтри, drag-and-drop, NEXT та релізи, люди на картці, Branch, чеклісти, сповіщення, автоматизації, shortcuts та чотири мови. Повторно прочитано офіційну документацію API. Нових змін / запитів запису до приватного Redmine або Trello не виконували. Код застосунку не створювали; тести реалізації й прав токена не запускали.

У RESEARCH.md внесено виправлення й реалізаційні рекомендації. Роадмапа за замовчуванням зберігається при зміні статусу, власні дії не створюють inbox-сповіщень. Для незавершених задач чинна умова готовності — Deploy; вже успішно завершені Done задачі при початку завершення пропускаються, а їх показ у складі релізу обов'язковий. Agile-функції після обговорення відхилені.

## 2. Знахідки

P1 — прогалина може втратити видимість задач / подій, створити дублікати або змінити не ті дані. P2 — неповний UX чи інтеграційний контракт. P3 — неоднозначність документа. Пріоритет стосується майбутньої реалізації, а не знайденого багу в наявному коді.

| R01 | P1 | Прихована завершена роадмапа могла приховати й незавершену задачу | Активна роадмапа визначає колонку; інакше задача повертається до групування за статусом. Невідома сутність не означає тихе вилучення |
| R02 | P1 | NEXT і конкретний реліз могли трактуватися як дві одночасні належності; shared versions розмивали межу проєкту | Одна Target version, перенос замінює її; перевірка власника Version та точного project ID. Модель приватної інсталяції ще перевірити |
| R03 | P1 | Попередній Assignee міг виявитися рев'юером, QA або тимчасовим Join, а не розробником | Розробник — окрема стала роль із відомим джерелом. Не вгадувати людину; передбачити явний вибір, якщо джерело ненадійне |
| R04 | P1 | «Пропускати вже завершені» суперечило вимозі Deploy для всього релізу; між перевіркою й закриттям міг змінитися склад | Повна перевірка перед першим записом, стійка операція, контроль складу перед закриттям. | R05 | P1 | Загальні retries могли дублювати створення задачі / NEXT / коментаря після timeout | Невідомий результат відокремлено від відмови. Перечитування, звірка операції, жодного сліпого повтору неідемпотентного запису |
| R06 | P1 | Timestamp без підтвердження всіх сторінок міг пропустити журнали; повторний polling міг дублювати inbox | Часове перекриття, event IDs, стійкий cursor лише після збереження подій, історичний baseline, окреме оновлення Versions / Watchers |
| R07 | P1 | CI-правило могло спрацювати на старий Failed або вже застарілий Review | Перевірка хронологічного переходу й актуального стану; загальна команда повернення розробнику; відновлення відділене від replay |
| R08 | P2 | Вимкнення власних дій могло заглушити потік для автоматизацій; Assignee на момент події не визначено | Inbox-фільтри відділені від журналів / тригерів. Підписка проєкту не звужує обов'язкові події призначених задач |
| R09 | P2 | Команда обиралася за видимою колонкою, хоча NEXT може містити Review / QA | Усі дії обираються за фактичним статусом, використовують однакові команди для DnD, меню й shortcuts |
| R10 | P2 | Не визначено формат опису, збереження редактора та прив'язку вкладень | Збереження raw-тексту, перевірка формату Redmine, очищення HTML, явні Save / Cancel, стійкі чернетки та видимі помилки файлів |
| R11 | P2 | На момент рев'ю чекліст погоджений, але його сховище могло непомітно переписувати опис | 2026-10-02 функцію відкладено; збереження / UI чеклістів не реалізовувати в поточному обсязі |
| R12 | P2 | Бракувало API-перевірок для проєктів, поточного користувача, людей, пріоритетів та фільтрів | Додано матрицю capability-перевірок; глобальний список users не є залежністю звичайного токена; підтримка параметрів перевіряється |
| R13 | P2 | Default приховування Done / Rejected могло стати незмінним фільтром усіх подань | Основна дошка має погоджений default, явне історичне / кастомне подання може включати закриті задачі |
| R14 | P2 | Shortcuts не описували відсутність активної картки, фокус, параметри статусу / label та Q / B | Контекст команд визначений; Cmd+C не забирає копіювання тексту; ті самі workflow-команди й перевірки прав |
| R15 | P2 | Backend описаний як необов'язковий, хоча потрібна фонова робота; persistence і token-контракт неповні | Backend / worker необхідний; локальна БД, volume, міграції, backup / restore, обмеження локального доступу й секрети без логування |
| R16 | P3 | «Усі питання закриті» могло означати повну технічну готовність; старі записи журналу та додаткові пропозиції змішувалися з рішеннями | Відділено продуктове погодження від API-перевірок; історичні формулювання позначені; Agile-пропозиції не включені до затвердженого обсягу |

Ключові джерела для API-висновків: [Issues](https://www.redmine.org/projects/redmine/wiki/Rest_Issues), [Versions](https://www.redmine.org/projects/redmine/wiki/Rest_Versions), [Users](https://www.redmine.org/projects/redmine/wiki/Rest_Users), [Memberships](https://www.redmine.org/projects/redmine/wiki/Rest_Memberships), [Issue Journals](https://www.redmine.org/projects/redmine/wiki/Rest_IssueJournals). Решта контрактів — інженерні рекомендації цього рев'ю; їх не слід приписувати як гарантії Redmine.

## 3. Що ще перевірити перед інтеграцією

1. Читання та права токена за кожним проєктом / tracker, IDs статусів, пріоритетів, Branch та Labels; підтримка фільтрів, Watchers і allowed statuses.
2. NEXT як Version і її власник; як обробляються locked / shared versions та clearing Target version. Якщо фактична модель інша, змінити адаптер, а не правила продукту.
3. Джерело й історія розробника та фактичного QA. Для задач із чужих клієнтів не обіцяти гарантованого відновлення ролей лише з останнього Assignee.
4. Для всіх екранів складу релізу читати задачі з усіма статусами; default основної дошки не приховує Done. API-перевірка чеклістів вилучена з поточного обсягу.
5. Required Branch під час створення, підтримуваний формат тексту, права вкладень / private notes, механізм захисту від конкурентних записів.
6. Дозволені записи перевіряти контрольованими сценаріями після підключення, відповідно до тодішньої авторизації. Нинішній read-only ресерч не є дозволом змінювати робочі задачі для тестів.

Ці перевірки не вимагають знову питати користувача про вже погоджені продуктові правила. Вони можуть обмежити реалізацію окремої можливості; обмеження потрібно показати, а не маскувати успішною дією.

## 4. Сценарії приймання реалізації

Це критерії для майбутніх перевірок, не звіт про виконані тести.

| № | Сценарій | Очікуваний результат |
| --- | --- | --- |
| A01 | Проєкт має понад 100 задач і кілька підпроєктів | Дошка читає потрібну область повністю, не втрачає колонки за pagination й не змішує проєкти |
| A02 | Review-задача призначена NEXT | Видима один раз у NEXT, показує Review й червоний значок |
| A03 | Роадмапа закрита, задача лишилась Review | Колонка роадмапи прихована; доступна задача видима за статусом, Target version не очищено |
| A04 | Явний фільтр включає Done / Rejected | Фільтр працює, default основної дошки не примусово вилучає ці задачі |
| A05 | NEXT → To Do без опції очищення / з нею | Статус зберігається; без опції картка лишається в NEXT, з опцією переходить у To Do; Review / QA повертаються розробнику |
| A06 | Задача з NEXT додається до конкретного релізу | Target version замінюється, задача не дублюється; інші задачі NEXT не зачіпаються |
| A07 | Review → QA, поточний користувач не Assignee | Виконується потрібне приєднання, перехід і кінцевий QA; стала роль розробника не губиться |
| A08 | QA / Review → To Do, розробник невідомий | UI просить вибір; worker фіксує необхідність дії й не призначає довільну людину |
| A09 | Частина незавершених задач релізу не Deploy; CI labels довільні | Неготовий статус блокує до першого запису; якщо решта Deploy, labels не додають заборони; вже Done пропускаються |
| A10 | Часткове завершення релізу й restart | Власні Done кроки не повторюються, невдалі можна відновити; Version не закривається передчасно |
| A11 | Після перевірки змінився склад / статус релізу | Зміна помітна, команда не оголошує повний успіх за старим знімком |
| A12 | Timeout створення задачі / NEXT / коментаря | Немає сліпого повтору й заяви про успіх; результат звіряється з сервером |
| A13 | CI In Progress → Failed, Review; або подія вже застаріла | Актуальна подія повертає розробнику в To Do один раз; застаріла не перезаписує нові зміни |
| A14 | Є підписка проєкту, але змінено фільтри дошки | Область підписки не змінюється, коментарі інших людей не губляться |
| A15 | Подія належить і Assignee-охопленню, і підписці; або це власна дія | Одна inbox-подія для чужої дії; власна відсутня в inbox, але лишається в історії / потоці правил |
| A16 | Закрита вкладка / restart Docker / збій сторінки синхронізації | Worker незалежний від вкладки; unread зберігаються, після restart дочитування не пропускає й не дублює події |
| A17 | Відкриття конкретної події / кнопка «Прочитано» одночасно з новим коментарем | Обидва способи архівують прочитані події; новий коментар лишається непрочитаним і підтримує favicon; відкриття панелі не читає все |
| A18 | Cmd+C у картці, у редакторі, з виділеним текстом і без активної картки | URL Redmine копіюється лише в потрібному контексті; звичайне копіювання тексту збережено |
| A19 | Збереження опису / файлу не вдалося; зміна мови або restart | Raw-текст і чернетка не губляться; форматування не змінюється непомітно, файл не позначається прив'язаним передчасно |
| A20 | Збереження ручного вибору розробника / фільтрів / shortcuts і restart | Додатковий стан відновлюється з БД; повернення Review / QA використовує запам'ятованого розробника; UI чеклістів відсутній |
| A21 | Перемикання uk / pl / es / en в незбереженій формі | Контекст і дані збережено; перекладені всі системні стани, форматування й множини коректні |
| A22 | Token без admin або окрема capability недоступна | Доступні функції працюють; немає обов'язкового /users списку, вигаданих ролей чи мовчки проігнорованих фільтрів |
| A23 | Реліз має Done, Deploy і задачі інших статусів; основна дошка приховує Done | У складі релізу видно всі задачі та правильні лічильники, default-фільтри дошки не успадковані |

## 5. Обсяг і порядок роботи

Погоджені функції не скорочено. Рекомендований порядок реалізації: деморежим і спільні команди → базовий UX / i18n / подання → адаптер API й capabilities → стійкі багатокрокові операції / worker → релізи / inbox / налаштування / перевірки відновлення. Докладний стек обрати окремо; без токена можна розробляти інтерфейс, локальний стан і контракт адаптера, але не заявляти сумісність із приватною інсталяцією.

Додаткові Agile-ідеї з [розділу 18 RESEARCH.md](RESEARCH.md#18-додаткові-agile-функції--відхилені) відхилені користувачем 2026-10-02 і не є планом робіт. Поточний обсяг також не включає чеклісти. 23 сценарії вище відображають чинні вимоги; A23 додано після уточнення показу Done у релізі. Погоджено пропуск уже Done задач при завершенні релізу. Розробка дозволена лише з read-only доступом до Redmine; мутації перевіряти в demo / mocks за AGENTS.md.
